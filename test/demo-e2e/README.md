# Demo end-to-end tests

`e2e.js` starts three local chains (chainId 11155111, 421614, 46630) on ganache, deploys the full V5 stack on each in the
same order (so contract addresses coincide across chains, as they do on the real testnets), injects a mock wallet into the
demo page and runs 18 checks in a real Chromium in the fixed-pool mode: registry loading (three networks, then network,
token and pool chosen in turn), faucet, deposit, withdrawal, the same pool address on two chains, a 6-decimals token, a
note from another network, double spend, disclosure, the no-wallet auditor tab (a valid proof is accepted, a proof made for
another one-time code is rejected), the legacy V4 pool, malformed and old-format notes, and the absence of JavaScript
errors. 18 of 18 passed on 2026-10-10, both on `demo/index.html` and on the reference app `sdk/demo-app-v5.html` (copied
into a folder as `index.html` next to `deployments.json`; the test handles its single pool list).

It needs the same setup as `router-e2e.js` (below): `test/distribution/node_modules`, Playwright with Chromium and the
browser bundles. The legacy V4 pool uses the verifier in `fixtures/WithdrawVerifierV2.sol` (generated by snarkjs for
`circuits/build/withdraw_v2`); all other contracts and circuit files come from the repository.

```
cd test/distribution && npm install && cd ../demo-e2e
sh build-bundles.sh
DEMO=/path/to/demo node e2e.js
```

It does not replace a test with a real wallet and live RPC endpoints.

## Native-coin network: `native-e2e.js`

The demo on a network whose gas coin is the pooled token, next to an ERC-20 network: native pools and router, a wallet
that has to add the network, the relayer stand-in, a visitor with no wallet. 16 checks with real proofs. `V6=1` runs the
same checks on the V6 pools and router (`withdraw_v4`, 20-level trees, relayer and fee in the proof):

```
DEMO=/path/to/demo node native-e2e.js
V6=1 DEMO=/path/to/demo node native-e2e.js
```

## Router features: `router-e2e.js`

Covers the demo's network/token selectors and the two router modes (deposit of any amount, withdrawal by amount and master
key). It deploys the real V5 pools and `LatheonDistributionPool` on three local chains, injects a mock wallet and uses real
Groth16 proofs. 36 checks: pool list shown only in the fixed modes; exact and rounded deposits (160, 99 → 90, 12 USDG with
6 decimals, 999 = 23 notes, refusal above 32 notes); the master key format; amounts that cannot be paid (nearest sum shown,
no transaction); wrong key, unknown router, malformed key; spent notes; partial withdrawals; separate notes withdrawn
through the ordinary one-note flow; a master key pasted where one note is expected gets a clear message; RU/ZH text; no JavaScript errors.

```
cd test/distribution && npm install && cd ../demo-e2e
sh build-bundles.sh
DEMO=/path/to/demo node router-e2e.js
```

It is a local test, not a replacement for a run with a real wallet. That was also done: see `STATUS.md`.

## Native-coin pools: `native-e2e.js`

For a network whose gas coin is the pooled token (`LatheonShieldedPoolV5Native`, `LatheonDistributionPoolNative`; in
`deployments.json` the token has `"native": true`, address zero, and the pools `"version": "v5-native"`). One local chain
with the native pools and router next to an ordinary ERC-20 network, a mock wallet that does not know the native network
yet, real Groth16 proofs. 16 checks: both networks listed; the wallet is asked to add the network with its own coin;
deposit steps say "Check the pool" and "No approval needed"; a 10 LTH deposit sent as the coin itself; the note
withdrawn to an empty address that then holds exactly 10; a router deposit of 161 as 1+1+1+1 notes with nothing left in
the router; withdrawal by amount and master key to an empty address; the separate gas-coin row hidden on the native
network and shown again on the ERC-20 one; the faucet-page link (`faucetPage`) and its Russian text; no raw i18n keys;
no JavaScript errors; and the network's relayer (`relayer` in `deployments.json`, simulated by the test): a withdrawal by amount and key sent by the relayer's account while the user pays nothing, and a visitor with no wallet at all withdrawing a note through it. 16 of 16 passed on 2026-10-21.

```
DEMO=/path/to/demo node native-e2e.js
```

## Log scanning: `rpc-robust.js`

Checks the block between `rpc-robust:begin` and `rpc-robust:end` in `demo/index.html` against fake endpoints modelled on
the real ones measured on 2026-10-10: an endpoint that answers any range (`sepolia-rollup.arbitrum.io` returned 2.1M
blocks in one request) must be read in exactly one request; a 50,000-block cap (publicnode) and a 10,000-block cap with
HTTP 400 (drpc free plan) are split until they fit; "could not coalesce error", "Failed to fetch" (a 429 without CORS
headers) and "pruned history unavailable" are retried; a contract error is not; an endpoint that is down stops after 40
failed requests with its original error; at most 8 requests are in flight; the log stays short; and
`sdk/demo-app-v5.html` carries a verbatim copy of the block. 13 checks, no network and no packages: `node rpc-robust.js`.
The demo also checks every scan against the pool's `nextIndex()` before it builds a proof.

## Website counters: `landing-e2e.js`

Opens `site/index.html` in Chromium with mocked RPC answers and checks the "Verify it yourself" cards: each shows the sum
of `nextIndex()` over that network's V5 pools, no explorer API is called, the label is translated (EN/RU/ZH), a network
that does not answer shows a dash and a link to its explorer, and there are no JavaScript errors. 9 checks:
`node landing-e2e.js` (Playwright with Chromium).

## Bridge page: `bridge-e2e.js`

Covers `bridge/index.html` on two local chains: a parent (chainId 421614) with the real `LatheonToken` and stand-ins for the
Orbit inbox, rollup and outbox, and a child (the Latheon chain id) with stand-ins for `ArbSys` and `NodeInterface` placed at
their fixed addresses (`fixtures/BridgeMocks.sol`). The test plays the chain's part: it credits deposits on the child and
confirms withdrawals on the parent. 18 checks: loading the bridge entry from `deployments.json`; balances on both chains;
refusals before any transaction (amount above the balance, malformed amount, bad address); a wallet RPC error named by step with its inner message; gas limits estimated by the page; a deposit with an approval for
exactly the amount, seen arriving; a withdrawal through `withdrawEth` (the wallet adds the chain with LTH as its coin);
waiting until a state covering it is confirmed, then the claim through `executeTransaction` with the right fields; finding a
withdrawal by its hash in another browser; RU/ZH; phone width; no JavaScript errors.

```
cd test/distribution && npm install && cd ../demo-e2e
sh build-bundles.sh
node bridge-e2e.js            # or BRIDGE=/path/to/folder/with/index.html
```

The stand-ins do not check Merkle proofs and do not reproduce the delay of the real chain. A run against the live test chain
is still needed and is recorded in `STATUS.md` once done.
